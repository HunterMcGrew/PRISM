# Hook Runtime

The hook runtime PRISM installs into a consumer's agent hosts: how `prism update` delivers it, the state it keeps, and the gates it enforces. Where the rest of an install lives and who owns it is [`install-layout.md`](./install-layout.md). How `prism adopt` and `prism update` run is [`consumer-sync-flow.md`](./consumer-sync-flow.md).

---

## Hook runtime

**Delivery path.** `prism update` copies the hook runtime into your `.claude/hooks/` whatever `hosts` in `.ai-skills/config.json` holds, including the git hook modules, the plan-chain modules under `plan/`, and the shell parser in `lib/tokenize.mjs` and `lib/segments.mjs` ([`plan-chain-scripts.md`](./plan-chain-scripts.md)). It copies the review and verify scripts under `review/` and `verify/` too ([`review-runtime.md`](./review-runtime.md)). `env-keys.mjs` is the secrets gate's remedy and runs as `node <file>`. The skills you receive name these scripts, and a Cursor user runs them from a terminal. The registrations, the two git hook shims in `.githooks/` ([`git-hooks.md`](./git-hooks.md)), and the `.gitignore` lines below follow `hosts` and arrive when it includes `claude` or `codex` (absent means every host). `prism update` also appends one line to your `.gitattributes`, `.prism/metrics/review-misses.jsonl merge=union`, whatever `hosts` holds, so two branches that each append rows to the review-misses log merge by keeping both sides' rows. It merges each host's registration (`.claude/settings.json`, `.codex/hooks.json`) only for that host. Both register `PreToolUse`, `PostToolUse`, `PostCompact`, and `UserPromptSubmit`, which only the approve guard uses. The Claude registration also adds `PreCompact`, and `SessionStart` with matcher `startup|resume|compact`. The Codex registration adds `SessionStart` with matcher `startup|resume`. On both, the `startup` and `resume` sources run the git hooks installer. Only the Claude registration matches `compact`, which runs the compaction note (§ Compaction arms). The merge works inside each event's list of entries. PRISM replaces only its own entries there, so a hook you registered on the same event survives every update. Dropping one host removes only its registration on the next update. Dropping both also removes the git hook shims, and the runtime files stay. The `.gitignore` lines described below stay after a host is dropped. Cursor is the only host with no registration today.

**How PRISM decides which hook entries in your settings are its own.** PRISM claims a hook entry in `.claude/settings.json` or `.codex/hooks.json` only when its command matches the exact shape PRISM writes. If you wrapped or edited that command, the entry is yours — PRISM neither refreshes it nor removes it when you drop its host from `hosts`, which means it can be left pointing at a runtime file the update took away. Keeping the match strict is deliberate: a looser one would let a removal delete a wrapper you wrote. `prism doctor` covers the gap instead. It reports, on every host mix, a registration whose command points at a missing file.

**State file.** The hook tracks which routed docs each scope has read in `.prism/architect-route-state.<scope-id>.json`, with a `.tmp` sibling while it writes. The read-tracking and git-gates state-file globs, with their `.tmp` siblings, are appended to your `.gitignore`, so the files stay out of your commits. Those lines are the only thing PRISM writes there. Nothing else in your `.gitignore` is touched. If the file is missing or unreadable the hook treats it as empty, which costs you a repeated announcement and nothing worse. The same file holds the umbrella speed bump's acknowledgements, so a read between a deny and its retry keeps them.

**Switches.** Set `PRISM_HOOK_DISABLE=1` to make the hook inert without unregistering it — useful when you want to keep the setup and turn the behavior off for a session. `PRISM_HOOK_DENY_DISABLE=1` switches off every deny but the secrets gate's and the approve guard's, leaving announcements on. The approve guard reads neither switch (§ Approve guard). The secrets gate reads neither, for the same reason (§ Secrets gate). The commit gate denies a command that assigns or exports either switch, which stops the plain forms an agent might write into its own command. It does not see a switch set behind a wrapper the parser doesn't walk, such as `sudo` or `xargs`, or one set in the environment before the session starts, so the switches stay friction and not a wall.

## Write gate

Touching a file your manifest routes to an architect doc is blocked until you have read that doc. Like the rest of the hook runtime, this reaches Claude Code and Codex. On Codex, PRISM answers with the deny format OpenAI documents for Codex hooks. That format is checked against the documentation but not yet observed in a live Codex session.

**What triggers it.** A `Write`, an `Edit`, or a `Bash` command naming a path one of your manifest routes matches, where at least one doc that route names has not been read in this scope. One rule covers all three, so deleting or moving a routed file asks for the same read a write does. On Claude Code a subagent is its own scope and reads for itself, so a doc its parent read still gates the child. On Codex the scope is the session, with no separate scope per subagent. A path no route matches is never blocked — routing a path is how you opt it in, so a fresh install blocks nothing in your own application code. A file edit that passes this check then meets the umbrella speed bump below.

**What clears it.** Read each doc the message names, in full. The message spells out the exact command — `cat <doc>`, one line per doc — because only a whole-file read counts. A `Read` with a line range, a `head`, or a `grep` that merely names the doc does not clear it. Read it, then retry the same call.

The `cat` line is a remedy every host can run, not the only one that works. A flagless `cat` is exempt from the gate, and a `Read` with no line range is not the kind of call it checks, so whichever tool you are already in can perform the read.

**Shell commands are exempt only where the command is provably a read.** Nothing short of a real shell can say what an arbitrary command does to a path it names, so the gate never tries to guess. It treats every path-shaped word in the command as a possible target, and only lets one go when the entire command is a set of commands known to write no file in your working tree, carrying only flags those commands cannot write through. Most of that set is commands that only read, such as `cat`, `grep`, `ls`, and a read-only `git` subcommand. The rest is `git` subcommands that write only inside `.git/`, such as `commit`, `add`, and `push`, so `git add` on a routed file is not blocked. Any remaining word that matches one of your routes is treated exactly like a write, and reading the doc clears it. The exemption exists because the remedy is a read: blocking a plain `cat` would block the very command the message asks for.

That means a command that only reads sometimes asks for a doc read anyway: a pipeline, a `$VAR`, a `find`, or any binary the gate does not recognize cannot be proven read-only. The bias is deliberate — an unnecessary read costs you a minute once, while a missed write defeats the gate silently. Unlike a message you can retry past, the read clears that route for the rest of the scope.

**Turning it off.** Set `PRISM_HOOK_DENY_DISABLE=1`, remove PRISM's `PreToolUse` entry from each host's registration file (`.claude/settings.json` for Claude Code, `.codex/hooks.json` for Codex), or delete `.claude/hooks/hook.mjs`. Any of the three works, and none of them is prevented — the gate is friction meant to be worth keeping, not a lock. `prism doctor` reports a hook missing one half, says per host whether the gate is installed and registered, and warns when a dropped host's registration is still on disk.

**How PRISM decides what in `.claude/hooks/` is yours.** Every file PRISM delivers there carries a marker line. A marked file belongs to PRISM and is replaced on each update, edits and all — there is no stored checksum that could tell your edit apart from an older PRISM version, so to adapt the runtime, copy it under a new name and strip the marker line. A file without the marker is yours. At a path PRISM delivers to, it is saved as `.bak` before PRISM's copy replaces it. Anywhere else it is never touched. If a marked file turns up at a path PRISM no longer ships, the update writes a `.bak` copy beside it before removing it, and that `.bak` is then left alone on every later run — deleting it is your call, not PRISM's.

### Umbrella-section speed bump

The `umbrellas` list in your `.prism/architect/manifest.json` names files where a new section is costly: docs that cover a wide area by design, and rule files. When a file edit adds a `##`–`######` heading one of them does not already have, the hook stops it once and tells you what the section costs. For a doc, it lists the routes that load it. For a rule file, it says when the rule loads, read off its `load:` key. Then it points you at [`writing-an-architect-doc.md`](../guides/writing-an-architect-doc.md) § Where new content goes. If the section really does apply everywhere that file reaches, retry the same edit and it passes.

- **What counts as new.** A heading no line of the file already has. A `#` title never counts, and neither does a line inside a fenced block. A file you are creating has no headings yet, so each one it carries is new. Shell commands never meet the speed bump.
- **On Codex.** `apply_patch` is the documented edit tool. The field names Codex's `Edit` and `Write` tools carry are unverified, and a wrong guess lets the edit pass.
- **How often.** Once per scope, file, and heading. The acknowledgement is saved before the stop, and if it cannot be saved the edit goes through instead. Compaction resets acknowledgements along with read credit. Parallel edits in one session can occasionally cost an extra stop, or let one edit through unstopped.
- **Getting it.** A new install's manifest lists `.prism/rules/*.md` and `.prism/custom/rules/*.md`. `prism update` never rewrites your manifest, so on an existing install you add the `umbrellas` key by hand. Add any of your own docs that cover a wide area. Cursor has no speed bump, for the same reason it has no write gate.

### Approve guard

Approving a plan-chain file is a person's act: you run `node .claude/hooks/plan/approve.mjs <path>` in your own terminal and press `y`, or you type `approve` in chat. `approve-guard.mjs` stops an agent from doing it for you. Both hosts register it on `PreToolUse` and on `UserPromptSubmit`, the one event nothing else in the runtime uses.

- **What it denies.** Running `approve.mjs` without a chat approval, changing a chain file's `status`, `approved_by`, or `approved_at` line with an edit tool, a shell command that names the chat approval token's file or a prompt-submit event, and a file edit whose target names the token file. A Claude `Edit` or `Write` is judged on its `file_path` alone. A Codex `apply_patch` call's target is its whole patch text, so a patch that names the token file anywhere is denied, even when the hunk edits another file. A file edit is not checked for the event name, so an edit that adds `UserPromptSubmit` to a registration file passes.
- **What it allows.** After you type `approve` in chat, exactly one bare command, `node .claude/hooks/plan/approve.mjs <path>`, and only in the session you typed it in. The token is `prism-chat-approval.json` in the repo's git directory, so it never appears in your working tree. It never expires, and it records a hash of every chain artifact, so `approve.mjs` refuses a file edited after you typed `approve`.
- **What counts as approving.** A sentence you wrote that says `approve` or `approved`. A question, a negation, quoted text, and a sentence that talks about approving rather than approves, with `to` just before the word or a hedge such as `if`, `could`, `will`, or `want` earlier in the sentence, never count.
- **Worktrees.** A session in a git worktree runs the copy its hook command names, which resolves through the directory the session started in, usually the main checkout. When the session's own checkout is another worktree of the same repository and holds a copy at the same path, the guard hands the event to that copy, so the command it names is the session checkout's own `approve.mjs`.
- **Shell it cannot read.** A command the guard can't parse is denied when it contains `approve`, and allowed otherwise.
- **Switches don't reach it.** It ignores `PRISM_HOOK_DISABLE` and `PRISM_HOOK_DENY_DISABLE`, because an approval path an agent can turn off is not a control. To stop using it, remove its entries from each host's registration file.
- **Accident backstop, not a sandbox.** It stops accidental runs and casual edits. A determined agent gets past it, for instance with `sed -i` on the frontmatter, so the real control is you reading the commit that carries `approved_by`. The header of `.claude/hooks/approve-guard.mjs` lists the known misses.
- **Hosts.** Claude Code and Codex. The Codex payloads were read off its documentation and not probed live. Whether a Codex hook's `session_id` equals the `CODEX_THREAD_ID` a command sees is unconfirmed. With `CODEX_THREAD_ID` set, a mismatch fails closed, since `approve.mjs` refuses a token from another session. A Codex session marked only by `CODEX_CI` or `CODEX_SESSION_ID` gives `approve.mjs` no session id to compare, so it skips that check and the guard's same-session check is the only one. Cursor has no prompt-submit delivery, so a Cursor user approves from a terminal with the keypress.
- **Read the plan docs first.** The approve command names a plan path, and the write gate routes plan paths, so a session that has not read the plan docs gets a read deny before the guard says anything. Read the docs the message names.

### Secrets gate

`secrets-gate.mjs` keeps an agent from putting a secret into a transcript. It denies a read of a secret file before the host runs it, and it points at a form of the same read that exposes no value. A path counts as a secret when it has a `.env` or `.env.*` basename other than `.env.example`, a `secrets` folder segment, or a `.pem` or `.key` basename. Matching ignores case, because a macOS disk reads `.ENV` as `.env`. Three arms judge a call. The read arm judges the `file_path` of Claude's `Read`. The search arm judges a Claude `Grep` whose `path` or `glob` names a secret shape, or whose search root holds one: it lists the root with `git ls-files -co --exclude-standard -z -s`, because ripgrep honors `.gitignore` the same way, and walks the root on disk when the root is itself ignored. A nested repo or submodule is one entry in its parent's list, so the gate lists it in turn, to a depth limit. From that list only a symlink and an untracked entry are resolved to a real path before they are judged, and a tracked file is judged by its listed name. The shell arm walks every simple command in a Claude `Bash` or `PowerShell` call, or a Codex `Bash` call, through the shell parser, and judges every word as a path, redirect targets and globs that could match a secret name included. It also judges the text after each letter of a short-option cluster, so `xargs -a.env` and `xargs -0a.env` are both read as the path `.env`, and the text after a word's first `=` or `:`. A relative path, a glob word, and a Grep `path` resolve against the real directory of the call's cwd, and a `..` climbs from the real directory of the path so far, so one after a symlink leaves the directory the link points at and not the link's own parent. A metadata program, `test`, `[`, `[[`, `stat`, `ls`, or `git check-ignore`, prints names and sizes and never content, so a call made only of those, with `echo`, `printf`, `true`, and `false` beside them, is judged on its redirect targets alone. The program must be a bare name, and the pass drops when anything could change which program a later name runs: an assignment, a function definition, a `${` or `$[` in any word, a `[[` arithmetic comparison, a `-v` test of an array element, or `printf -v` or an `=` in a `printf` argument after the format. `ls -la .env` passes, and `ls < .env` still denies.

`secretPaths` in `.ai-skills/config.json` adds patterns to the built-in ones, in the manifest route syntax, matched without regard to case against the repo-relative path. It never removes a built-in. A value that is not a list of strings, or a config that does not parse, keeps the built-ins alone and writes one stderr line.

The one exempt way to read a secret's contents is `node .claude/hooks/env-keys.mjs <file>`, exactly one segment with one file word and no redirect, pipe, assignment, or substitution, where the script is matched by realpath so a copy elsewhere is judged like any other command. `env-keys.mjs` prints a dotenv file's key names and never a value. It refuses a file not named like a dotenv file, a file that opens a PEM block, and a file that holds, outside a quoted value, a bare run of 16 or more base64 characters with no `=`, or a key whose value is only `=`, such as `Abc==`. Dotenv has no unquoted continuation line, so those are the middle and the tail of a wrapped base64 value, which would otherwise read as key names. A key file prints nothing. One residue is accepted: a single-padded tail with no middle line, such as `Abc=`, reads as an empty key and prints. The deny text names that command, written relative to the directory the command runs in, so it works from a subdirectory, and names `.env.example` as the other way to read the shape of a config.

Claude registers it on `PreToolUse` with matcher `Read|Grep|Bash|PowerShell`, and Codex with `^Bash$`, both with a timeout of 21 seconds. Codex has no read tool, so a Codex agent reads a file through the shell and the shell arm is the only one that reaches it. It reads neither kill switch (§ Switches), because a secrets path an agent can turn off is not a control. It fails open on its own crash, with one stderr line and no reply.

**One long word is judged in linear time.** A call that hands the gate a very long word must not push it past its 21-second timeout, because a hook that times out denies nothing. So a file name attached to a short option is read from the first 8 letters of the cluster only, and a longer cluster before the name is a known gap. A path of more than 256 segments is resolved as written, with no on-disk step through a `..`. A glob word in a command over 8 KB, or one spelled more than 16 times, is read as unquoted, which can deny a quoted glob.

**It is a backstop, not a sandbox.** A read through a program the walk cannot see into, such as `node -e`, a script file, or `cat $F`, passes, and so does a recursive search that names no secret path, such as `grep -r KEY .`. A few harmless commands are denied too, such as `cp .env.example .env`, or on Windows a search term spelled `\.env`, which there names a file at the drive root, because a word is judged without knowing whether the program reads or writes it. So is a quoted glob inside a shell string, such as `bash -c "ls '.env*'"`, because a quote is read only in the outer command's own words, and so is a quoted glob in a command over 8 KB or spelled more than 16 times, because it then reads as unquoted. The header of `.claude/hooks/secrets-gate.mjs` lists the known misses and accepted false denies.

### Commit gate

`commit-gate.mjs` judges an agent's commit before the host runs it. A commit that sweeps a sibling session's staged files, hides behind `--no-verify`, or carries a subject the plan can't read costs a review round to find, so the gate denies it up front. It reads the first commit out of a shell command, which is a `git commit` or a `node <runtime>/plan/commit.mjs "<subject>" <paths>` call, and it reads a `git push` for the bypass forms only. One script serves Claude Code and Codex, and a host with no shell call to read passes.

It denies on the first failure, in this order. A command that assigns or exports `PRISM_HOOK_DISABLE` or `PRISM_HOOK_DENY_DISABLE` is judged first, before any config read, on any command and in any repo. A `git push` in a repo with `.prism/architect/manifest.json` is judged next, and `--no-verify` and `-c core.hooksPath=` are the only denies a push gets. A command with no commit then passes, and so does a commit in a repo with no manifest. A commit whose directory the gate can't resolve gets the flag denies and nothing more. Otherwise the flag denies come next, and they hold on every branch: `-a`, `-i`, `--no-verify` or `-n`, `-c core.hooksPath=`, a named path the shell would expand, a `:` pathspec magic on `git commit`, and more than one commit in one command. While a merge, cherry-pick, or revert is in progress only the flag denies run, so the concluding commit may name no paths. When none is in progress, a named path that takes the whole repo, such as `.` at the root, is denied next with the `-a` reason, and the gate goes on to the index and the four checks.

The gate builds the tree the commit would produce in a temporary index and runs four checks in this order. The config check and the index run on every branch of such a repo. The subject check, the weakened-tests check, and the stop-path half of the stops check read the branch's plan, so they run only on a folder-plan branch, where the plan the branch name resolves is a chain file directly under `.prism/plans/<folder>/`. A flat plan, an archived plan, and a branch with no plan skip them.

- **Config.** A `.ai-skills/config.json` that does not parse, or a `stopPaths` or `testGlobs` value the plan scripts reject, denies the commit. A check that skipped on a config it could not read would let the commit through unchecked.
- **Subject.** The subject starts with `T<n>:`, `T<a>-T<b>:`, `T<a>,T<b>:`, `T<n> fix:`, `plan:`, or `retro:`. A `plan:` commit names only the branch's own plan folder, and a `retro:` commit names only the promotion paths and the plan folder. The promotion paths are `.prism/retros/`, `.prism/lessons.md`, `.prism/archived/lessons-archive.md`, `.prism/metrics/review-misses.jsonl`, `.prism/architect/`, `.prism/spec/adrs/`, and `.prism/rules/`, the generated copies of the last three under `.claude/`, `.codex/`, and `.cursor/`, `AGENTS.md`, and `templates/install/.prism/`. The check reads a task subject's form, not whether the plan holds the task it names.
- **Weakened tests.** A commit that removes a line from a test file needs a named task that lists the file and carries `behavior change:`. A line the branch itself added doesn't count. The test files are the `testGlobs` config key, which falls back to `*.test.*`, `*.spec.*`, and the `test`, `tests`, and `__tests__` directories at any depth. A list that is set replaces the default, and a pattern holding `{` is a config error because braces never expand.
- **Stops.** A change to a dependency entry needs a named task that lists the file and carries `new dependency:`, and a change to a contract path needs a named task that lists it. The stop paths are the ones plan approval reads. For dependency entries the gate reads the four npm dependency fields and the composer `require` and `require-dev` fields, and any other dependency file counts on any change. This check also denies a commit that names no paths, so that deny comes last, after the other three, and never runs while a merge concludes or on a directory the gate can't resolve.

The would-be index is a temporary file, so the gate never stages anything in the shared index, and each git call gives up after 5 seconds. A `commit.mjs` call is a `node` segment whose script resolves by native realpath to this runtime's `plan/commit.mjs`, so a copy elsewhere reads as no commit, and its index is built with `--literal-pathspecs`, as the script commits. The gate fails open on any error in the hook itself, because a gate that breaks a commit on its own bug blocks every agent. The hook exits at once, before it reads stdin, when either switch is `1` in its own environment.

Claude registers it on `PreToolUse` with matcher `Bash|PowerShell`, and Codex with `^Bash$`, both with a timeout of 21 seconds. The known misses live in the headers of `.claude/hooks/commit-gate.mjs` and `.claude/hooks/commit-gate/parse.mjs`, and each check's in its own module. They include `git revert`, `git cherry-pick`, `git merge`, and `git am`, which create commits without a `git commit` segment.

## Compaction arms

Auto-compaction summarizes a session with no guidance, so your corrections, open questions, and decisions never written to the plan get dropped. A compact also skips a skill's startup, so nothing prompts the session to re-read its plan afterward. Two compaction arms cover both gaps in Claude Code.

- **Before a compact (`PreCompact`)** the hook prints a summary template. Claude Code uses that output as the instructions for the summary. The template names eight sections, says what to leave out, and carries the branch, plan path, and `git status -s` read from disk, so the summary copies those facts instead of recalling them.
- **After a compact (`SessionStart`, source `compact`)** the hook prints a note into the compacted context: re-read the plan, write unrecorded decisions into its `## Decisions`, then resume the active skill. Other session starts print no note. A `startup` or `resume` runs the git hooks installer instead, which prints one line only when it set `core.hooksPath`.

The plan path comes from your branch's ticket ID, matched against `ticketPrefix` in `.ai-skills/config.json` and resolved by the shared lookup in `plan/lookup.mjs`: plan folders and flat plans by name, then a scan for the ticket in each plan's `ticket:` or `## Ticket` field, then the same lookup under `.prism/archived/plans/`. On a miss, the template tells the summarizer to keep every decision, since the summary may be the only record, and the post-compact note sends the session to the full Plan Lookup in `branch-plan.md` before it concludes no plan exists. Text you type after a manual `/compact` appears to reach the summarizer alongside the template. That was observed in one live manual compact. The Claude Code docs say only that the hook receives your typed text as `custom_instructions`. Another `PreCompact` hook that prints to stdout, yours or a plugin's, likely adds to the summary instructions too. How Claude Code combines several hooks' output is unverified. Every failure prints nothing and lets the compaction proceed. `PRISM_HOOK_DISABLE=1` turns both arms off with the rest of the runtime. Codex gets neither arm, because PRISM has not verified that Codex uses hook output to shape its compaction summary. Its `SessionStart` registration serves only the git hooks installer.
