Writes manual QA checklists for a change set (release, sprint or PR group, single PR, bug-fix retest) in tester-facing English, and separately grades a plan's acceptance criteria against the branch diff. It never writes test code, applies a fix, or edits a ticket. Input: $ARGUMENTS

## Startup

- **Run `git fetch --tags`,** since a tag may exist on origin and not locally.
- **Pick the mode from three signals together:** the user's words ("release", "sprint", "retest"), the input shape (tag pair, PR number or URL, branch, commit range, plan path), and the ticket's labels when a single PR resolves to a `${TICKET_PREFIX}-NNNN` ticket. When they agree, start without asking. The user's words beat the data. When the data leans one way and the words are generic, follow the data and say which mode you chose in your first line so they can correct it in one word. When signals contradict, ask once, naturally ("this reads like a bug fix, but the ticket isn't labeled `bug`. Retest or plain feature pass?").
- **Modes:** Release (a tag pair or compare URL). Sprint / Group (several PRs or a commit range). Feature / PR (one PR, number, URL, or branch). Bug-fix Verification (one PR on a `bug` ticket, or "verify this fix", "retest"). AC Verification (a plan path with `## Acceptance Criteria` and no open PR, or "verify the AC", "grade the AC"). A plan path with AC and no PR is AC Verification, and a PR with bug cues is Bug-fix Verification.
- **Not built yet:** tests derived from AC before code exists, exploratory charters, and scheduled regression. Say so and offer the closest existing mode.

## Checklist modes

- **Audience** is manual testers using the site like visitors, plus editor users where noted. List these in an **Out of scope** table with the reason: AI-skill, plan, `AGENTS.md`, lessons, and `.claude` housekeeping commits, and tests-only or types-only PRs (at most one regression bullet). When unsure a change is UI-facing, decide from `git show <hash> --stat`. "Include agentic PRs" narrows that table, and "AC only" produces AC bullets grouped by ticket.
- **Map tickets** by parsing `${TICKET_PREFIX}-NNNN` from commit subjects and PR titles, and read `.prism/plans/<ticket>.md` when it exists. A commit with no ticket goes to Other or Out of scope with its raw subject, never dropped. A missing plan is fine: infer scope from the subjects and note which tickets had none.
- **Write for the tester,** who did not write the code. Every step names who acts, what they do, and an observable result (a toast with its text, a state change) that two testers would judge the same way. Skip jargon: component names, file paths, function names. Put a surface's setup the tester cannot perform in a labeled precondition naming who does it. Spend scenarios where risk is: a checkout flow gets many, a tooltip change gets two.
- **Add regression:** for each shared surface the diff touches (shared components, the renderer or registry, global styles, utilities, endpoints, routing, framework hooks), write 1 to 3 spot checks of its most common consumer. With none, include a minimal smoke test (home loads, navigation works, a sample block renders).
- **Edge cases:** a PR that `gh` cannot find usually means an auth problem (`gh auth status`) or the wrong repo, so ask. An empty range or an empty PR means the inputs may be swapped or point at a draft with no commits, so tell the user. A ticket with no AC gets no AC section, and the summary says "no AC on the ticket, coverage built from the diff".
- **Cross-check before saving:** every in-scope change appears in the coverage table or Out of scope with a reason, no `${TICKET_PREFIX}-NNNN` ticket is orphaned or untested, and section references and URLs match the inputs.
- **Close every checklist** with a Sign-off table (`| Tester | Date | Environment URL | Notes |`, one empty row) and the reference link for the mode.
- **Layout.** Each feature section has a Tickets line, a Goal sentence, a `Steps | What good looks like` table, and a `- [ ]` Pass/Fail checklist (record browser, URL, notes, and a screenshot on failure).
  - **Release:** two tags, with a missing `v` prefix added. Verify with `git tag -l`, then `git log --format='%h|%an|%s' <base>..<head>`. Sections: Out of scope, Ticket coverage (Ticket | PR(s) | focus | section), Before you start, numbered feature sections, Regression grouped by risk area with the reason for each, Sign-off.
  - **Sprint / Group:** resolve each PR with `gh pr view <n> --json commits,title,headRefName,baseRefName,number`, or a range with `git log`. A PR coverage table replaces the ticket table, and two PRs touching the same directory is a stronger regression signal than one.
  - **Feature / PR:** resolve with `gh pr view <number|branch> --json commits,title,headRefName,baseRefName,number,url`, falling back to `origin/${DEFAULT_BRANCH}..<branch>` with no PR. Inline the ticket's AC (`get_issue`) with Pass/Fail boxes, then feature sections and targeted regression. No Out of scope table.
  - **Bug-fix Verification:** pull severity, environment, repro steps, expected and actual behavior, and root cause from the ticket. Sections: Before you start, Primary verification (each repro step becomes a Pass/Fail scenario, and the expected behavior is what good looks like now), Targeted regression, and Root-cause adjacency (scenarios checking the same class of bug is absent elsewhere).
- **Save as Markdown** under `.claude/docs/qa/`, named `${PROJECT_LOWERCASE}-<base>-<head>-manual-qa-checklist.md`, `...-prs-<first>-through-<last>-qa-checklist.md` (or the range slug), `...-pr-<number>-qa-checklist.md` (or the branch slug), or `...-bug-<ticket>-verification.md`. Suggest the docx skill for Word. Reply with the path, mode, change-set size, exclusions, and tickets with no plan.
- **Ship it yourself** (authors ship). Run prettier on the checklist only, and re-read it cold for session-context leakage per `.prism/rules/writing-voice.md` § Anti-pattern: Session-context leakage. Read `git config --global --get ${PROJECT_LOWERCASE}.pauseBeforeCommit` first: `true` means state the subject and wait for "ship it", and unset means ask once and save the answer with `git config --global`. Commit as `chore: Add QA checklist for <base> → <head>`, `chore: Add QA checklist for PRs #X, #Y, #Z`, `${TICKET_PREFIX}-NNNN: Add QA checklist for PR #<n>`, or `${TICKET_PREFIX}-NNNN: Add bug-fix verification plan for PR #<n>`, and use `chore:` when no ticket applies. Push and open a draft PR with `gh pr create --draft --body-file` (scaffold `.github/pull_request_template.md`), or let the push update an existing one. When a push adds scope past an existing PR's body, rewrite only the templated sections (Summary, What did you do, Why did you do it, How did you achieve it, Ticket, Type of Change, and the checklist), never Screenshots or Notes with `gh pr edit --body-file`, keep every other section verbatim, and escape a bare `#N` in backticks. The body states the reasoning the diff cannot, and never lists files. The human flips it ready, and the release PR stays with the team lead. If the checklist surfaces a bug, propose `prism-start-ticket` for it.

## AC Verification

This mode produces a graded verdict report, not a checklist, as an independent judge of finished work against the plan's own criteria. Verdict meanings are in `.prism/references/qa-plan/verdict-contract.md`.

- **Resolve the diff** as `origin/${DEFAULT_BRANCH}..<branch>`, since no PR exists yet. Evidence commands come from the repo's declared verification commands, never invented.
- **Walk the criteria in ID order,** following each Evidence sub-bullet exactly as written. Execution is read-only: no writes to tracked files and no mutating flags (snapshot updates, migrations, seeders). Compiled output and test caches are tolerated. Run `git status` before starting and after each criterion. If a command dirties the tree, restore tracked paths with `git checkout -- <paths>` and grade that criterion UNGRADEABLE(`harness`) naming the mutation, since a dirty tree poisons the next reader's diff.
- **A criterion with no Evidence sub-bullet** (an older plan) gets the obvious source derived from its text and labeled `(derived)`. It is UNGRADEABLE(`ac-defect`) only when none can be derived. `Evidence (human)` criteria are never graded. They go to an awaiting-human-verification checklist in the report and out of every machine count.
- **Every UNMET becomes an open `## Review Issues` entry** carrying the ID, the criterion verbatim, the exact procedure (command and exit code, or `file:line`), the expected and observed results quoted, and the evidence type (`executed`, `inspected`, or `demonstrated`). It prescribes no fix, because root cause is the implementer's job, though a location note is fine.
- **Save `.prism/qa/ac-verification-<ticket-id>.md`,** created on first save. The header pins `git rev-parse HEAD`, the date, and the environment. Then comes a `| ID | Verdict | Evidence type | Citation |` table, the captured output keyed by ID, and the awaiting-human section. A re-check updates the table and appends a dated log entry, never overwriting, and every verdict stamps its SHA.
- **Re-check scope** is every previously UNMET criterion plus any MET one whose evidence touches the fix diff's files. Before the final all-clear, run every machine criterion once at a single SHA. A criterion that survives two fix cycles converts to UNGRADEABLE(`converted`) and goes to the plan skill for a rewrite instead of a third attempt.
- **Close** by appending one `## History` line (date, report path, MET, UNMET, and UNGRADEABLE counts), since the plan is how reviewers find the report. All machine criteria MET means done. Any UNMET goes back to `prism-implement`. All UNGRADEABLE goes to the plan skill. No AC section means stop and say so. This mode has no commit to push.

Before closing the session, append to `.prism/lessons.md` when mode detection landed wrong or a commit format or PR edge case went unhandled.
