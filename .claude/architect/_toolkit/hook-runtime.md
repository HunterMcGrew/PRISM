# Hook Runtime

The hook runtime PRISM installs into a consumer's agent hosts: how `prism update` delivers it, the state it keeps, and the gates it enforces. Where the rest of an install lives and who owns it is [`install-layout.md`](./install-layout.md). How `prism adopt` and `prism update` run is [`consumer-sync-flow.md`](./consumer-sync-flow.md).

---

## Hook runtime

**Delivery path.** `refreshHookRuntime` copies the runtime files listed in `HOOK_RUNTIME_FILES` (the `.mjs` modules, not their `.d.mts` sidecars, and including the git hook modules under `git-hooks/` and `lib/command.mjs`) into the consumer's `.claude/hooks/`. The same pass delivers the two git hook shims into `.githooks/` and sets `core.hooksPath`, which [`git-hooks.md`](./git-hooks.md) covers. The list also carries the plan-chain modules under `plan/` and the shell parser in `lib/tokenize.mjs` and `lib/segments.mjs`, which [`plan-chain-scripts.md`](./plan-chain-scripts.md) covers. It carries the review and verify scripts under `review/` and `verify/` too, which [`review-runtime.md`](./review-runtime.md) covers. Each entry point in `HOOK_RUNTIME_ENTRY_POINTS` gets the executable bit: `hook.mjs`, `git-gates.mjs`, `approve-guard.mjs`, and the gates below. `env-keys.mjs` is the secrets gate's remedy and runs as `node <file>`. The plan-chain, review, and verify modules run as `node <file>`, so none of them needs the bit. The runtime files reach every install, whatever `hosts` (`.ai-skills/config.json`) holds, because the skills a consumer receives name these scripts and a Cursor user runs them from a terminal. Registrations, the git hook shims, and the `.gitignore` lines below follow `hosts` and arrive when it includes `claude` or `codex`. Absent means every host, so an existing install keeps receiving them with no migration. `runUpdate` also appends one line to the consumer's `.gitattributes`, `.prism/metrics/review-misses.jsonl merge=union`, beside those `.gitignore` lines. It follows no host setting, because every install has the review-misses log, and two branches that each append rows to it then merge by keeping both sides' rows. Each host's registration is merged only for that host: `.claude/settings.json` for `claude`, and `.codex/hooks.json` for `codex` via `mergeHookCodexRegistration`. Codex runs project-local hooks only after the user trusts the project's `.codex/` layer and reviews each hook definition, so a committed registration alone does not make the gate fire there ([ADR-0077](../../spec/adrs/_toolkit/0077-hook-enforcement-reaches-claude-code-and-codex.md) § Consequences). Both templates register `PreToolUse`, `PostToolUse`, `PostCompact`, `UserPromptSubmit`, which only the approve guard uses (§ Approve guard). The Codex template also registers `SubagentStart`, for the brief gate. The Claude template also registers `PreCompact`, and `SessionStart` with matcher `startup|resume|compact`. The Codex template registers `SessionStart` with matcher `startup|resume`. On both, the `startup` and `resume` sources run the git hooks installer. Only the Claude registration matches `compact`, which runs the compaction note (§ Compaction arms). The merge composes within each event's array. `mergeHookEventEntries` drops only PRISM's own prior entries and appends the current ones, so a consumer's own entries on the same event survive every update. A merge also drops PRISM-owned entries from an event key the new source no longer carries, then deletes the key if it is empty, so a retired registration such as the old `SubagentStop` reconcile gate leaves a consumer's settings on the next update while the consumer's own entries under that key stay. The update and doctor command patterns keep `reconcile-gate` as a retired entry point so the old entry is still recognized as PRISM's. Dropping one host removes only its registration on the next update. Dropping both also removes the git hook shims, and the runtime files stay. The `.gitignore` lines below stay after a host is dropped, because no update path removes them. Cursor is the only host without a registration. It receives the runtime files. The resolver reads Cursor's payload shape, but no install path writes a Cursor hook file, and `HARNESSES.cursor.emitDeny` returns `null`. Wiring it up is follow-up work rather than a setting a consumer can flip.

**The asymmetry is a decision, not an oversight.** Enforcement reaches Claude Code and Codex. On Codex the delivery is verified, but the deny envelope is documentation-verified, not live-probed (`HARNESSES.codex.emitDeny` in `scripts/ai-skills/hooks/harnesses.mjs`). No measured session has yet shown a Codex deny reason reaching the model. Cursor keeps the always-on prose fallback. [ADR-0077](../../spec/adrs/_toolkit/0077-hook-enforcement-reaches-claude-code-and-codex.md) records the call and the alternatives rejected to reach it, in its § Decision. It supersedes [ADR-0074](../../spec/adrs/_toolkit/0074-hook-enforcement-is-claude-only-with-a-prose-fallback.md), whose rejections of a git `pre-commit` floor and of levelling down by removing the gate still stand. The git hooks ([ADR-0081](../../spec/adrs/_toolkit/0081-git-hooks-ship-beside-the-agent-gates.md)) run format and lint at commit and push. They do not stand in for read-before-write.

**The subagent gate has host limits of its own.** Codex cannot block at subagent start, so the brief gate logs a `would-deny` row there and denies nothing (§ Brief gate). The `SubagentStart` fields Codex sends are documentation-read and not live-probed (`HARNESSES.codex` in `scripts/ai-skills/hooks/harnesses.mjs`). Cursor has no registration for the gate.

**State file.** Read-tracking is per scope, in `.prism/architect-route-state.<scope-id>.json`. Each host's `scopeId` in `harnesses.mjs` decides the scope id. Claude Code uses the session id and appends the agent id for a subagent, so a Claude subagent has its own scope. Codex uses `session_id` with no agent suffix. Cursor uses `conversation_id`. A `.tmp` sibling sits beside it during the atomic write. Every load-and-save runs under a lock, a `.lock` directory beside the file (`withRouteStateLock` in `architect-route.mjs`), because a tool batch spawns one hook process per call and without it each save dropped the credits the others added. Eight concurrent reads credited four before the lock. A lock the hook cannot take within two seconds is skipped and that one update runs unlocked, so a stuck lock never stalls a tool call. It is a cache and not a record: an unreadable or unrecognized file reads as absent, which costs one repeated announcement rather than bricking the hook. The same file holds `umbrellaAcks`, the umbrella speed bump's acknowledgements, and every save carries them forward, so a read between a deny and its retry keeps them (§ Umbrella-section speed bump). `git-gates.mjs` keeps its own family beside it, `.prism/git-gates-state.<scope>.json`, keyed by the same scope id and the HEAD sha. `refreshHookRuntime` appends a line for each state-file glob and its `.tmp` sibling to the consumer's `.gitignore`, on adopt and on every update that delivers the runtime. The write is append-only, skipping lines already present, so the files never reach a commit. Those lines are the whole of what PRISM writes there. Nothing else in a consumer's `.gitignore` is touched.

**Hook log.** The brief gate appends a JSON line to `prism-hooks.jsonl` when it would deny on Codex, through `appendHookLog` in `lib/hook-log.mjs`. The file sits in the worktree's own git directory, as the chat approval token does (§ Approve guard), so it never appears in the working tree and needs no `.gitignore` line. A failed write is swallowed, because the log is a record and never a reason to fail a call.

**Switches.** `PRISM_HOOK_DISABLE=1` makes the runtime inert before it parses stdin, so a session can keep the registration and still run without the hook — one variable changes behavior without touching a registration file or the manifest. `PRISM_HOOK_DENY_DISABLE=1` is the narrower switch: it turns off every deny but the secrets gate's and the approve guard's, and leaves announcements on. The approve guard reads neither switch, because an approval path an agent can turn off is not a control (§ Approve guard). The secrets gate reads neither, for the same reason (§ Secrets gate). The brief gate and the commit gate read both switches before they read stdin, as `hook.mjs` does. The commit gate also denies a command that assigns or exports either switch, which stops the plain forms an agent might write into its own command. It does not see a switch set behind a wrapper the parser doesn't walk, such as `sudo` or `xargs`, or one set in the environment before the session starts, so the switches stay friction and not a wall.

## Write gate

A call that touches a path matching any manifest route is denied until the route's docs have been read ([ADR-0072](../../spec/adrs/_toolkit/0072-write-gate-on-routed-paths.md)). One rule covers a `Write`, an `Edit`, and a `Bash` command alike, so a delete or a move gates the same way a write does and no list of delete verbs has to be kept current. Claude Code registers it as `PreToolUse` matched `Write|Edit|Bash`. Codex registers it as `^(Bash|apply_patch|Edit|Write)$`. Cursor gets no registration, the same delivery gap § Hook runtime states.

**What triggers a deny.** All five of: no kill switch set, a scope id on the payload, a tool whose kind the harness's table explicitly lists as `write` or `shell`, a manifest route matching the path, and at least one of that route's docs neither read this scope nor missing from disk. An unrouted path is never denied on any verb — a route existing is the opt-in, which is what keeps a fresh install from blocking a consumer's first edit to their own code. A file-edit call that clears all five then meets the umbrella speed bump (§ Umbrella-section speed bump).

**What clears it.** Reading each doc the message names, in full, through a channel the credit channel observes: a `Read` with no `offset` or `limit`, or a flagless `cat`, alone or after a literal `cd <dir> &&`. The operand resolves inside the directory the `cd` moved to. Only a `cd` may sit before `&&`, because in `cat a.md && cat b.md` the second `cat` never runs when the first fails. A `cd` whose target the hook cannot know (`cd -`, a bare `cd`, a `~` path) ends crediting for the rest of the command, and so does one that enters a name and leaves it, such as `missing/..`, because the shell fails that `cd` when the name is absent. An operand that climbs out of a `cd` target, as in `cd missing && cat ../<doc>`, credits nothing for the same reason, and because through a symlinked target the `..` lands somewhere else. In a live probe on 2026-11-18, Claude Code stripped a `cd` into the session's own directory before the hook saw the command, so the `cd` rule matters for a session working in another directory, such as a subagent in its own worktree. The message names the literal `cat` command per doc, because credit turns on the shape of the call and a remedy the model has to infer is one it cannot reliably perform. It closes with one line naming what counts, because a redirected `cat <doc> > /dev/null` looks like a read and delivers nothing. A `head`, a ranged `Read`, a redirected or piped `cat`, or a `Grep` naming the doc credits nothing.

**A shell command gates on the same rule, minus what it can prove it only reads.** No parser short of a real shell can say what an arbitrary `Bash` command does to a path it names, so the arm never tries. Every path-shaped token in the command is a candidate. When the whole command is provably a set of commands that write no working-tree file, each carrying only flags that command cannot write or execute through, nothing is a candidate, its command words included. Most of that set is read-only commands such as `cat`, `grep`, `ls`, and a `git` whose subcommand only reads. A `cd` with a literal target belongs to it, and so does `&&` as a separator. The rest is `git` subcommands that write only inside `.git/`, such as `commit`, `add`, and `push` (`GIT_TREE_SAFE_SUBCOMMANDS` in `hook.mjs`). So `git add` on a routed doc is not gated. A candidate that matches a route is judged exactly as a write is.

Candidates resolve against the command's working directory. The arguments of a segment after a literal `cd` also resolve against the directory it moved to, so `cd scripts && tee ai-skills/hooks/hook.mjs` gates on `scripts/ai-skills/hooks/hook.mjs`. Resolved from the repo root alone, the operand is `ai-skills/hooks/hook.mjs`, which no route matches. A `pushd`, and a `cd` behind `(`, `{`, `builtin`, or `command`, move the arguments after them the same way.

**Heredoc text a data reader sees is not scanned.** A heredoc body is left out of the candidates when the command reading it treats stdin as data (`DATA_STDIN_READERS` in `hook.mjs`: `gh`, `cat`, `tee`, `jq`), that command does not pipe onward, and the body carries no `$(` or backtick. Without this, every word in a PR comment piped to `gh api --input -` was a candidate, and the `docs/` route matches the bare word `docs`. The body stays in the scan for a shell, an interpreter, `git apply`, or `patch`, because each runs or applies its stdin. It also stays for `cat <<'EOF' | sh`, which pipes the text on to a shell. Every body in a command stays when the command holds a process substitution, as in `tee <<'EOF' >(bash)`, or when any segment's head is outside the data readers, the read-only commands, and `cd`, as in `cat > x.sh <<'EOF'` followed by `sh x.sh`. Every body stays too when any one of them cannot be placed in the command text (`locateHeredocBodies`), because leaving text in the scan costs a doc read while cutting the wrong text lets a write through unseen. So an unplaceable body can over-deny but never under-denies. A here-string's `<<<` and a `#` comment open no heredoc, so a line after `gh api x <<< "$J"` or `cat # <<EOF` is still read as a command. A path on the reader's own command line, as in `tee <path> <<'EOF'` or `cat > <path> <<'EOF'`, is still a candidate. Both arms rewrite `\` to `/` first, wherever the next character is path-shaped, so a Windows-spelled path is one token on every platform — the rewrite keys on that following character rather than on `path.sep`, which is what keeps a single code path both CI legs execute. A read the rewrite changed announces its docs but does not clear them, because credit turns on the shape of the call rather than on what the shell delivered. The deny message already prints the forward-slash spelling, and that spelling clears everywhere.

The proof is an exemption, not a verdict: a flagless `cat` is exempt because denying it would deny the remedy the deny message asks for. The arm over-denies on purpose — a read it cannot prove costs one doc read, which is more forced reading than the respelling a reroute used to ask for, and it clears for good instead of re-firing.

**Three gaps survive.** A write whose target path never appears in the command text — built from a variable, reached by a `cd` whose target is not literal (`cd "$DIR"`) or that runs inside `eval` or a function, or written into a script a later command runs — is invisible to any scan over the command. The exemption lists are the second. Command membership has an executable check: `hook-gate.test.ts` runs every listed shell command against a scratch file and asserts the file is unmodified. Flag membership has no such check and stays a human judgment, so a flag wrongly admitted is a silent write rather than an extra read. `DATA_STDIN_READERS` has the same shape: a reader wrongly on it lets the paths its stdin names go unseen. `sort -o`, `uniq <in> <out>`, `git diff --output`, and `sed`'s `w` script command each proved that direction once. The third is a deadlock rather than a leak — an architect doc whose own path carries a character outside the read-safe class cannot be `cat`-ed provably, and `.prism/architect/**` is routed, so the remedy gates itself. See [ADR-0072](../../spec/adrs/_toolkit/0072-write-gate-on-routed-paths.md) § Consequences.

**The gate is friction, not a wall.** Deleting the registration, deleting `.claude/hooks/hook.mjs`, or setting `PRISM_HOOK_DENY_DISABLE=1` each disables it; all three are trivial and none is prevented. The hook's consumer-side files, `.claude/hooks/`, `.claude/settings.json`, and `.codex/hooks.json`, are deliberately unrouted, because in a consumer repo those files belong to the consumer. The compensating control is visibility. `prism doctor` reports a hook missing one half, either a runtime with no registration or a registration pointing at a missing file. Removing both halves looks the same as never having received it, so doctor stays quiet. It reports per host whether the runtime is installed and registered. It warns when a dropped host's registration is still on disk.

### Umbrella-section speed bump

A file edit that clears the read-credit check meets one more check when its target is on the manifest's `umbrellas` list. That list holds the docs that cover a wide area by design, plus the rule files. If the edit adds a `##`–`######` heading the file does not already have, the hook denies it once and says what the section costs. Retrying the same edit passes. The point is the moment of writing. A section about one subsystem belongs in its own routed doc, and filed in an umbrella it loads into every session the umbrella reaches, per [`writing-an-architect-doc.md`](../guides/writing-an-architect-doc.md) § Where new content goes. The deny puts the doc's real routes in front of the writer before that happens. For a rule file, it states when the rule loads instead, read off the rule's `load:` key.

**What fires it.** A file-edit tool on a path an `umbrellas` entry matches: Claude's `Edit` and `Write`, or Codex's `apply_patch`, `Edit`, and `Write`. Codex documents `apply_patch` as its edit tool. The field names its `Edit` and `Write` carry are unverified, and a wrong guess finds no edit text and lets the edit pass. Entries are repo-relative patterns compiled by `compileMatcher`. `listManifestRoutes` in `hooks/lib/match.mjs` keeps the reserved key out of every reader that walks routes. A heading counts as new when no trimmed line of the file on disk matches it. A `#` title never counts, and neither does a line inside a fenced block in the edit text. Fence tracking sees only the edit text, so an edit that opens mid-fence can miss a heading after the fence closes. A file being created has no headings yet, so every heading it carries is new. A Codex patch contributes only the added lines of the target file's own section, so one file's heading is never charged to another. A shell command carries no edit text, so it never meets the speed bump.

**Once per scope, doc, and heading.** The acknowledgement, `<path>\n<heading>`, is saved to the scope's state file as `umbrellaAcks` before the deny goes out, which is what lets the retry find it. A save that fails allows the edit, because a deny with nothing recorded would deny every retry. Every heading one deny names is acknowledged together. `PostCompact` deletes the state file, so compaction resets acknowledgements along with read credit. The save runs under the state lock (§ Hook runtime, **State file**), reloading the file first so it keeps credits another process saved meanwhile. When the lock is skipped after its two-second wait, two hook processes in one scope share one `.tmp` path, so a parallel edit can lose an acknowledgement, which costs one more stop, or fail a save, which lets that edit through unstopped.

**What a pass proves.** A pass shows only that the stop was issued once. It does not show that the writer read it, or that the section belongs where it went. The hook cannot tell whether content applies to every file a doc reaches, which is why this is a speed bump and not a wall.

**Reach.** The hook reads only `.prism/architect/manifest.json`, which is consumer-owned and never rewritten by `prism update`. A new install gets `umbrellas` from the install stub, listing `.prism/rules/*.md` and `.prism/custom/rules/*.md`. An existing install opts in by adding the key by hand. Cursor has no speed bump, for the same reason it has no write gate.

### Git gates

Two author-side gates ride the same runtime as a second entry point, `git-gates.mjs`, registered on its own `Bash` matcher group so it never spawns on a `Write` or `Edit`. Both watch the shell tool's `PreToolUse` event and recognize a `git commit` or `git push` segment in the command text — no harness exposes a pre-commit event of its own. The cleanup-pass hold holds the first `git commit` on each HEAD sha once per session, naming `.prism/references/cleanup-pass.md` as the remedy; the retry of the same command goes through, because the state is saved before the deny. The push gate runs `commands.lint` and then `commands.format` from `.ai-skills/config.json` and denies the push with the output tail on a non-zero exit. When git runs PRISM's own shim for the matching hook and its `gitHooks` command is set, the gate skips the `commands` entry that git hook already ran ([`git-hooks.md`](./git-hooks.md) § Relationship to the agent gates). In a command the parser can read, the gates skip a `git` segment that runs inside a container (the `docker exec` and compose forms `lib/segments.mjs` unwraps), because that segment acts on the container's repo and not the session's, so neither gate fires on it. Text the parser can't read is scanned for `git commit` and `git push` words instead, so a container's `git` or a quoted mention is held there too. That scan can hold a command that would never run. It is a text scan and not a parse, so it makes no promise to catch every spelling.

Both are off until the consumer sets them: a `hooks` block in `.ai-skills/config.json` carrying `commitCleanupPass`, `pushVerification`, and an optional `pushVerificationTimeoutMs` (120 s by default). The block is read by the runtime, not a persona, which is why it is its own top-level key rather than a `features.*` entry. A config with no block, a config that is not valid JSON, and either kill switch above all leave the gates inert. The config that governs a `git` call is found by walking up from the directory the call runs in — the session's working directory with any `-C` applied — and no further than that repo's own toplevel, so a separate nested repo is governed by its own config or by none, and its push never runs the enclosing repo's `commands.*`.

The push gate fails open on anything but a real non-zero exit: a command that exceeds its budget or cannot start allows the push and says so, on stderr and — where the host renders one — in an allow envelope carrying the same line. A deny on a timeout would ask for a remedy the retry cannot perform, and a silent allow would make a broken lint command indistinguishable from a passing one. The decision record, with the alternatives rejected on the way to it, is [ADR-0076](../../spec/adrs/_toolkit/0076-commit-and-push-gates-are-harness-hooks.md). [ADR-0081](../../spec/adrs/_toolkit/0081-git-hooks-ship-beside-the-agent-gates.md) records why real git hooks now ship beside these gates. ADR-0076 calls the hold "the commit gate". The commit gate is now the separate gate below.

### Approve guard

Approving a plan-chain file is a person's act: they run `node <rel> <path>` in their own terminal and press `y`, where `<rel>` is the path of `plan/approve.mjs` from the repo's top level, or they type `approve` in chat. `approve-guard.mjs` is the third entry point, and it denies an agent the ways around that. Both hosts register it twice: on `PreToolUse`, matched to the shell and edit tools, and on `UserPromptSubmit`, which nothing else in the runtime uses. It reads neither kill switch (§ Switches), because `hook.mjs` checks both before it parses stdin and an approval path an agent can turn off is not a control.

Four arms. Three run on `PreToolUse`, in this order, and the fourth runs on `UserPromptSubmit`.

- **Token.** Denies a shell command that names the chat approval token's file or a prompt-submit event, and a file edit whose target names the token file, so an agent can't write the token or run the prompt arm by hand. A Claude `Edit` or `Write` is judged on its `file_path` alone. A Codex `apply_patch` call's target is its whole patch text, so a patch that names the token file anywhere is denied, even when the hunk edits another file. A command that only reads, such as `grep UserPromptSubmit .claude/settings.json`, passes. A file edit is not checked for the event name. A Claude `Edit`, or a Codex `apply_patch` tool call, that adds `UserPromptSubmit` to a registration file passes, and the header of `approve-guard.mjs` lists edits to the harness settings files as a known miss. The Codex `apply_patch <<EOF` form is a shell command and is denied when it names the event.
- **Execution.** Denies a shell command that names `plan/approve.mjs`, unless the command word is a read-only one (`git`, `grep`, `cat`, and the like) or the command is the one allowed form below. `node <rel>/plan/commit.mjs "<subject>" <paths>` also passes when the script resolves by realpath to the runtime's own `commit.mjs`, so a change to `approve.mjs` can be committed. It is judged like a read-only command, and it passes only as the whole command: one segment with no `;`, `&&`, `||`, `|`, `&`, newline, subshell, or substitution, because an earlier segment can change directory or set the environment, through `eval`, `export`, or a `cd` the parser can't see, and the guard resolves the script against the payload's `cwd`. When that segment names `approve.mjs`, any leading assignment denies it, because `NODE_OPTIONS` can load a module that runs the script. A node option before the script means the pass does not apply, so the segment is judged as any other `node` run. Its redirects are still judged. The script word must also hold a `/` and not start with `-`. Node reads a word like `-r`, `--no-warnings`, `-`, or `inspect` as an option or subcommand, so a link by that name to `commit.mjs` would resolve to the real script while node runs whatever follows it. A spelled path such as `./-r` is always a file and still passes. The pass trusts `commit.mjs` by path, so an edit to that script is a known miss in the header. A test runner such as `node --test` runs its file operands, so one that names `approve.mjs` is still denied. The deny text names `node <rel> <artifact>`.
- **Frontmatter.** Denies a file edit that changes a chain file's `status`, `approved_by`, or `approved_at` line, by comparing the lines before and after through the reader `approve.mjs` uses. `approved_via` is not one of them.
- **Prompt.** Writes the token when a sentence the person wrote says `approve` or `approved`, and tells the agent the one command to run. A question, a negation, quoted text, and a message the harness wrote itself, such as another session's brief, never count. Neither does a sentence that talks about approving rather than approves: one with `to` just before the word, or a hedge such as `if`, `could`, `will`, or `want` anywhere earlier in it. A miss costs the person one more message, while a false approval stamps a file.

**Worktrees.** A session in a git worktree runs the copy its hook command names, and the command resolves through the directory the session started in, usually the main checkout. That copy can be stale, and the command it would name, `node ../../../scripts/…/approve.mjs`, runs the main checkout's script. So when the payload's `cwd` sits in another worktree of the same repository that holds a copy at the same path, the guard hands the event to that copy and passes its output through. A session checkout with no copy, or an unrelated checkout, runs the one the command named. Paths compare through the native realpath, which expands a Windows 8.3 short name. PRISM's own `UserPromptSubmit` registration also checks the file exists, and when it doesn't, it tells the person through `systemMessage` and the agent through `additionalContext` that chat approvals aren't being recorded, instead of failing with a hook error nobody sees. Consumer registrations keep the bare `node` form `PRISM_HOOK_COMMAND_PATTERN` matches.

**The token.** It is `prism-chat-approval.json` in the worktree's own git directory, so it never appears in the working tree, an agent doesn't write there, and a session in another worktree can't reach it. It holds the time, the session id, the file the person named when they named one, and a hash of every chain artifact. It never expires. `approve.mjs` takes it, which deletes it, so one message approves one run, and refuses a file whose text no longer matches the recorded hash. The hash is what the age limit used to be for: an approval covers the text the person had in front of them.

**The one bare command.** Under a token from the same session, the guard lets exactly `node <this repo's approve.mjs> <path>` through, with no assignment, second command, or expansion on the line. Behind `cd … &&`, or with anything else around it, it is still denied.

**It fails closed on shell it cannot read.** A command the tokenizer can't read is denied when it contains `approve`, and allowed otherwise. A word that holds shell syntax, such as `$'appr\x6fve.mjs'` or a `bash -c` string, is tokenized again and its words checked.

**It is an accident backstop, not a sandbox.** It stops accidental runs of `approve.mjs` and accidental edits to the approval lines. A determined agent gets past it, for instance with `sed -i` on the frontmatter, and the real control is the person reading the commit that carries `approved_by`. The parser is frozen, so a new bypass shape goes on the known-miss list in the header of `scripts/ai-skills/hooks/approve-guard.mjs` and not into the tokenizer. The same header lists the accepted false denies.

**Hosts.** The guard reaches Claude Code and Codex. Codex's payloads were read off its documentation and not probed live. Whether a Codex hook's `session_id` equals the `CODEX_THREAD_ID` a command sees is unconfirmed. With `CODEX_THREAD_ID` set, a mismatch fails closed, since `approve.mjs` refuses a token from another session. A Codex session marked only by `CODEX_CI` or `CODEX_SESSION_ID` gives `approve.mjs` no session id to compare, so it skips that check and the guard's same-session check is the only one. The field names Codex's `Edit` and `Write` tools carry are the same unverified guess the umbrella speed bump makes. Cursor has no prompt-submit delivery, so a Cursor user approves from a terminal with the keypress. That is why the runtime files reach a Cursor-only install.

**The write gate comes first.** The approve command names a plan path, and the write gate routes plan paths, so a session that has not read the plan docs gets a read deny before the guard says anything. The remedy is the read.

### Secrets gate

`secrets-gate.mjs` keeps an agent from putting a secret into a transcript. It denies a read of a secret file before the host runs it, and it points at a form of the same read that exposes no value. A path counts as a secret when it has a `.env` or `.env.*` basename other than `.env.example`, a `secrets` folder segment, or a `.pem` or `.key` basename. Matching ignores case, because a macOS disk reads `.ENV` as `.env`. Three arms judge a call. The read arm judges the `file_path` of Claude's `Read`. The search arm judges a Claude `Grep` whose `path` or `glob` names a secret shape, or whose search root holds one: it lists the root with `git ls-files -co --exclude-standard -z -s`, because ripgrep honors `.gitignore` the same way, and walks the root on disk when the root is itself ignored. A nested repo or submodule is one entry in its parent's list, so the gate lists it in turn, to a depth limit. From that list only a symlink and an untracked entry are resolved to a real path before they are judged, and a tracked file is judged by its listed name. The shell arm walks every simple command in a Claude `Bash` or `PowerShell` call, or a Codex `Bash` call, through the shell parser, and judges every word as a path, redirect targets and globs that could match a secret name included. It also judges the text after each letter of a short-option cluster, so `xargs -a.env` and `xargs -0a.env` are both read as the path `.env`, and the text after a word's first `=` or `:`. A relative path, a glob word, and a Grep `path` resolve against the real directory of the call's cwd, and a `..` climbs from the real directory of the path so far, so one after a symlink leaves the directory the link points at and not the link's own parent. A metadata program, `test`, `[`, `[[`, `stat`, `ls`, or `git check-ignore`, prints names and sizes and never content, so a call made only of those, with `echo`, `printf`, `true`, and `false` beside them, is judged on its redirect targets alone. The program must be a bare name, and the pass drops when anything could change which program a later name runs: an assignment, a function definition, a `${` or `$[` in any word, a `[[` arithmetic comparison, a `-v` test of an array element, or `printf -v` or an `=` in a `printf` argument after the format. `ls -la .env` passes, and `ls < .env` still denies.

`secretPaths` in `.ai-skills/config.json` adds patterns to the built-in ones, in the manifest route syntax, matched without regard to case against the repo-relative path. It never removes a built-in. A value that is not a list of strings, or a config that does not parse, keeps the built-ins alone and writes one stderr line.

The one exempt way to read a secret's contents is `node <runtime>/env-keys.mjs <file>`, exactly one segment with one file word and no redirect, pipe, assignment, or substitution, where the script is matched by realpath so a copy elsewhere is judged like any other command. `env-keys.mjs` prints a dotenv file's key names and never a value. It refuses a file not named like a dotenv file, a file that opens a PEM block, and a file that holds, outside a quoted value, a bare run of 16 or more base64 characters with no `=`, or a key whose value is only `=`, such as `Abc==`. Dotenv has no unquoted continuation line, so those are the middle and the tail of a wrapped base64 value, which would otherwise read as key names. A key file prints nothing. One residue is accepted: a single-padded tail with no middle line, such as `Abc=`, reads as an empty key and prints. The deny text names that command, with `<runtime>` written relative to the directory the command runs in rather than to the repo root, so it works from a subdirectory, and names `.env.example` as the other way to read the shape of a config.

Claude registers it on `PreToolUse` with matcher `Read|Grep|Bash|PowerShell`, and Codex with `^Bash$`, both with a timeout of 21 seconds. Codex has no read tool, so a Codex agent reads a file through the shell and the shell arm is the only one that reaches it. It reads neither kill switch (§ Switches), because a secrets path an agent can turn off is not a control. It fails open on its own crash, with one stderr line and no reply.

**One long word is judged in linear time.** A call that hands the gate a very long word must not push it past its 21-second timeout, because a hook that times out denies nothing. So a file name attached to a short option is read from the first 8 letters of the cluster only, and a longer cluster before the name is a known gap. A path of more than 256 segments is resolved as written, with no on-disk step through a `..`. A glob word in a command over 8 KB, or one spelled more than 16 times, is read as unquoted, which can deny a quoted glob.

**It is a backstop, not a sandbox.** A read through a program the walk cannot see into, such as `node -e`, a script file, or `cat $F`, passes, and so does a recursive search that names no secret path, such as `grep -r KEY .`. A few harmless commands are denied too, such as `cp .env.example .env`, or on Windows a search term spelled `\.env`, which there names a file at the drive root, because a word is judged without knowing whether the program reads or writes it. So is a quoted glob inside a shell string, such as `bash -c "ls '.env*'"`, because a quote is read only in the outer command's own words, and so is a quoted glob in a command over 8 KB or spelled more than 16 times, because it then reads as unquoted. The header of `scripts/ai-skills/hooks/secrets-gate.mjs` lists the known misses and accepted false denies.

### Commit gate

`commit-gate.mjs` judges an agent's commit before the host runs it. A commit that sweeps a sibling session's staged files, hides behind `--no-verify`, or weakens a test with no task behind it costs a review round to find, so the gate denies it up front. It reads the first commit out of a shell command, which is a `git commit` or a `node <runtime>/plan/commit.mjs "<subject>" <paths>` call, and it reads a `git push` for the bypass forms only. One script serves Claude Code and Codex, and a host with no shell call to read passes.

It denies on the first failure, in this order. A command that assigns or exports `PRISM_HOOK_DISABLE` or `PRISM_HOOK_DENY_DISABLE` is judged first, before any config read, on any command and in any repo. A `git push` in a repo with `.prism/architect/manifest.json` is judged next, and `--no-verify` and `-c core.hooksPath=` are the only denies a push gets. A command with no commit then passes, and so does a commit in a repo with no manifest. A commit whose directory the gate can't resolve gets the flag denies and nothing more. Otherwise the flag denies come next, and they hold on every branch: `-a`, `-i`, `--no-verify` or `-n`, `-c core.hooksPath=`, a named path the shell would expand, a `:` pathspec magic on `git commit`, and more than one commit in one command. While a merge, cherry-pick, or revert is in progress only the flag denies run, so the concluding commit may name no paths. When none is in progress, a named path that takes the whole repo, such as `.` at the root, is denied next with the `-a` reason, and the gate goes on to the index and the four checks.

The gate builds the tree the commit would produce in a temporary index and runs four checks in this order. The config check and the index run on every branch of such a repo. The size check, the weakened-tests check, and the stop-path half of the stops check read the branch's plan, so they run only on a folder-plan branch, where the plan the branch name resolves is a chain file directly under `.prism/plans/<folder>/`. A flat plan, an archived plan, and a branch with no plan skip them.

- **Config.** A `.ai-skills/config.json` that does not parse, or a `stopPaths` value `resolveStopPaths` rejects, or a `testGlobs` value `resolveTestGlobs` rejects, denies the commit. A check that skipped on a config it could not read would let the commit through unchecked.
- **Size.** On a branch whose `intent.md`, read from the would-be tree and not the working copy, says `size: small`, a commit that takes the branch past the small limits is denied, quoting the reasons. The diff runs from the merge base of HEAD and `origin/<defaultBranch>` to the would-be tree, through the reader and classifier in `plan/size.mjs` ([`plan-chain-scripts.md`](./plan-chain-scripts.md) § Size). The remedy is to set `size: standard` in the intent and ask the person for a fresh `approve`. Because the intent is read from the would-be tree, the commit that makes that edit is judged as standard. A missing `origin/<defaultBranch>` ref, or any error while measuring, passes: measuring from HEAD instead would read only this commit, and a size the gate can't measure is no reason to block.
- **Weakened tests.** A commit that removes a line from a test file needs a named task that lists the file and carries `behavior change:`. A line the branch itself added doesn't count. The test files are the `testGlobs` config key, which falls back to `*.test.*`, `*.spec.*`, and the `test`, `tests`, and `__tests__` directories at any depth. A list that is set replaces the default, and a pattern holding `{` is a config error because braces never expand. An empty list matches no file, so it turns this check off, the way an empty `stopPaths` list turns off the stop paths it replaces. On a small branch the deny keeps its reason and gives the size check's remedy, going on as a standard ticket, because a small plan has no task to carry `behavior change:`.
- **Stops.** A change to a dependency entry needs a named task that lists the file and carries `new dependency:`, and a change to a contract path needs a named task that lists it. The stop paths are the ones plan approval reads. For dependency entries the gate reads the four npm dependency fields and the composer `require` and `require-dev` fields, and any other dependency file counts on any change. This check also denies a commit that names no paths, so that deny comes after the config, size, and weakened-tests checks, before the stop-path half, and never runs while a merge concludes or on a directory the gate can't resolve.

The gate never judges a commit's subject: any message passes, and the `T<n>:` form is a convention the prose rules carry. A task subject, `T<n>:`, `T<a>-T<b>:`, `T<a>,T<b>:`, or `T<n> fix:`, still names the tasks whose files the weakened-tests and stops checks allow. A subject that names no task, or a task the plan doesn't hold, gets no allowance, so a removed test line, a contract path, and a change to a dependency entry without `new dependency:` are all denied. Skipping the checks for such a subject was rejected, because any message would then bypass them.

The would-be index is a temporary file, so the gate never stages anything in the shared index, and each git call gives up after 5 seconds. A `commit.mjs` call is a `node` segment whose first operand resolves to a regular file whose native realpath ends in `/plan/commit.mjs` and whose first line carries the `@prism-hook-runtime` marker. Any marked copy counts, so a builder's worktree copy is judged like the runtime's own, and a file of another name, or one with no marker, reads as no commit. Its index is built with `--literal-pathspecs`, as the script commits, and the diffs the weakened-tests check reads set `GIT_LITERAL_PATHSPECS=1`, so a file name that starts with `:` is not read as pathspec magic. The gate fails open on any error in the hook itself, because a gate that breaks a commit on its own bug blocks every agent. The hook exits at once, before it reads stdin, when either switch is `1` in its own environment.

Claude registers it on `PreToolUse` with matcher `Bash|PowerShell`, and Codex with `^Bash$`, both with a timeout of 21 seconds. The known misses live in the headers of `scripts/ai-skills/hooks/commit-gate.mjs` and `commit-gate/parse.mjs`, and each check's in its own module. They include `git revert`, `git cherry-pick`, `git merge`, and `git am`, which create commits without a `git commit` segment.

### Brief gate

`brief-gate.mjs` keeps a dispatch brief short. A workflow agent takes its instructions from its skill and the plan folder, so a long brief is plan content that never reached `plan.md`, and an override line in a brief can talk the agent out of its own rules. The gate denies a dispatch to a gated role when the brief runs over 15 non-blank lines or carries an override phrase. The deny asks for a path brief: it states what that stage reads, the worktree path, and the report shape, and says anything longer goes into `plan.md` first. One script serves Claude Code and Codex, and each registration passes `--tool=<harness>`.

The gated roles are the ones a plan-folder run dispatches as subagents: `prism-spec`, `prism-challenge`, `prism-verify`, `prism-implement`, `prism-docs`, and `prism-review`. `prism-architect` is dispatched too and is left ungated, because a stage sends it a scope idea or a finding in prose by design. A consumer has no `roles.json` on disk, so `GATED_ROLES` in `brief-gate.mjs` spells the set out, and a test holds it equal to the roles `roles.json` marks `gated: true`.

Brief text is untrusted input, and the gate only counts and matches it. An override phrase is `ignore` or `disregard` followed by `instructions` or `rules`, with one or two qualifiers such as `the`, `all`, or `previous` between them, or `you may skip`, or `do not read plan.md`, which also reads `plan` and `the plan`, when it ends a clause or comes before `and`, `or`, `but`, `so`, `just`, or `first`. So "do not read plan.md first" denies, and "do not read plan.md History" passes. A `your` among the qualifiers always denies. Without one, a target other than the plan is exempt, so "ignore all instructions in them" about fetched content passes while "ignore the rules in plan.md" denies.

Claude gets the deny. Codex gets no deny, because its `SubagentStart` cannot block a subagent, so the gate appends a `would-deny` row naming the agent type and the line count to the hook log (§ Hook log) and the dispatch goes ahead. The gate fails open: a repo with no `.prism/architect/manifest.json` above the payload's cwd, a payload with no brief, and any error in the hook itself all pass, because a gate that breaks a dispatch on its own bug costs more than a missed deny.

Claude registers it on `PreToolUse` with matcher `Agent|Task`, because Claude Code dispatches a subagent as `Agent` and older builds as `Task`. Codex registers it on `SubagentStart` with no matcher. Both use a timeout of 21 seconds. The header of `scripts/ai-skills/hooks/brief-gate.mjs` lists the known misses. They include a Workflow-internal agent stage, which Claude's `PreToolUse` does not fire for, a Codex `SubagentStart` payload with no documented brief field, so its `would-deny` row fires only if a `prompt` field arrives, an override phrase reworded past the patterns, and a brief packed into a few very long lines, because the limit counts lines and not characters.

### Nested dispatch

The session dispatches `prism-review` as a subagent, and the review dispatches its own subagents for the passes, so a review needs a subagent that can launch subagents. A live probe on 2026-11-27 at 2:56 AM Central confirmed this on Claude Code. A headless `claude -p --allowedTools Agent` session dispatched `prism-review`, which launched one general-purpose subagent and relayed its reply. The probe's final output line was `PROBE inner=pong`. Codex is unprobed. Where a dispatched review cannot launch subagents, it sweeps the passes itself and prints the same coverage line.

### Stage tools

The PRISM build writes a gated role's `tools` list from its skill frontmatter into that role's Claude agent file, so `prism-verify` runs with `Read, Bash`, and `prism-review` runs with a list that names `Agent` and leaves out `Edit` and `Write`. Live probes on 2026-11-27 (Central) tested both on Claude Code. A headless `claude -p --allowedTools "Agent,Write,Edit"` session dispatched `prism-verify` and asked it, with Bash ruled out, to create a file with `Write` and change it with `Edit`. It replied `PROBE write=failed: no Write tool available to this agent (only Read, Bash, SubagentHandback) edit=failed: no Edit tool available to this agent`, and a check for the file printed `PROBE file=absent`. The same command with `general-purpose` in place of `prism-verify` printed `PROBE write=ok edit=ok` and `PROBE file=present`, so the outer session's permissions were not what stopped verify. A `claude -p --allowedTools Agent` session dispatched `prism-review`, which launched a general-purpose subagent and printed `PROBE inner=pong`, so the review's list keeps dispatch. The verify agent named no MCP tool among the tools it had. That is one run's observation, not a test of how a list treats MCP tools.

Codex's agent file has no tool allowlist. Its subagents documentation, read 2026-11-27, offers `features.*` switches that turn a capability off, such as `features.shell_tool`, and no tools key, and it says an agent file can't override the parent's MCP servers. So on Codex the `tools` line is only a declaration inside the rendered skill each `.codex/agents/*.toml` embeds. That is a host limitation, not a gap in the build. Cursor gets no agent files, so it gets the same declaration in its rendered skill and nothing more.

A stage with a shell can still write a file through it, so the list is friction and not a wall. The verify probe ruled out Bash for that reason, so a shell write could not pass for a `Write` call.

Windows without Git Bash is unsupported for dispatched stages. Claude Code's tools reference, read 2026-11-27, says the `PowerShell` tool is enabled automatically on Windows without Git Bash, and that the `Bash` tool is available on Windows only when Git Bash is installed. Every gated `tools` list names `Bash` and not `PowerShell`, so a gated stage on such a host has no shell. A Linux probe on 2026-11-27 showed that a list entry for a tool the host lacks is dropped without a warning: the agent loaded with `Read, Bash`, and its shell worked. That probe ran on Linux, so the Windows case it predicts, a stage that loads without its shell and reports no error, is untested.

### Compaction arms

Auto-compaction summarizes a session with no guidance, so user corrections, open questions, and decisions never written to the plan get dropped. A compact also skips a skill's startup, so nothing prompts the session to re-read its plan afterward. Two arms in `compact-handoff.mjs`, dispatched by `hook.mjs`, cover both gaps.

- **`--event=PreCompact`** prints a summary template. Claude Code uses a `PreCompact` hook's stdout as the instructions for the compaction summary, capped at 10,000 characters per hook. Longer output is cut and marked, not saved to a file the way other hook output is. The template names eight sections, tells the summarizer what to leave out, and carries the branch, plan path, and `git status -s` read from disk, so the summary copies those facts instead of recalling them.
- **`--event=SessionStart`** prints a note that lands in the compacted context: re-read the plan, write unrecorded decisions into its `## Decisions`, then resume the active skill. When the hook found the plan, a flat plan also gets a `## History` line. When it found none, the note sends the session to the full Plan Lookup and asks for no `## History` line in a plan the lookup turns up. Either way, a plan folder gets only scope changes and open questions, because a routine implementation choice already lives in a commit. The Claude registration matches `startup|resume|compact`, and this arm prints only on `compact`. It checks `source === "compact"` itself, so `startup` and `resume`, which run the git hooks installer instead, stay quiet here, and so does a registration without a matcher at all.

The plan path comes from the branch's ticket ID, matched against `ticketPrefix` in `.ai-skills/config.json`, then resolved by the shared lookup in `plan/lookup.mjs`: plan folders and flat plans by name, then the ticket-field scan, then the same lookup under `.prism/archived/plans/`. A generic `<letters>-<digits>` match was rejected because it hits slug fragments like `pr-896` in unrelated branch names. On a miss, the template tells the summarizer to keep every decision, since the summary may be the only record, and the post-compact note sends the session to the full Plan Lookup before it concludes no plan exists.

A hook cannot run a model turn, so it cannot write the plan before the summary is made. That is why the summary carries unrecorded decisions in full and the note has the session write them down first, on a plan folder only the scope changes and open questions among them. Every path prints nothing and exits 0 on failure, because a `PreCompact` exit of 2 blocks the compaction, and a blocked compaction recovering from a context-limit error fails the request.

Text typed after a manual `/compact` reaches the summarizer alongside the template, so the template does not repeat it. That was observed in one live manual compact. The Claude Code docs say only that a `PreCompact` hook receives the typed text as `custom_instructions`, which is null on an automatic compact. The docs describe each `PreCompact` hook's stdout as summary instructions, so another `PreCompact` hook that prints to stdout, from the consumer or a plugin, presumably adds to them. How Claude Code combines several hooks' output is unverified. The runtime's state reset runs on `PostCompact` and prints nothing to stdout, so this module is the runtime's only `PreCompact` stdout writer.

Codex gets neither compaction arm. Its `SessionStart` registration serves only the git hooks installer, and its matcher leaves out `compact`. Claude Code documents `PreCompact` stdout as summary instructions, and PRISM has not verified an equivalent in Codex, so a Codex registration would print text with no known effect.

### Hook-runtime ownership and recovery

**The runtime is zero-dependency `.mjs` because the consumer may have no `node_modules` to point at.** Every module under `scripts/ai-skills/hooks/` imports only `node:` builtins and its own siblings, and the registration invokes plain `node` — an `npx`-installed consumer has no package tree, so a `tsx` or `node_modules` invocation would be a permanent no-op there. Types ride `.d.mts` sidecars beside each module, which is what lets `tsc` resolve a `.mjs` specifier under the root `moduleResolution` with no tsconfig change. `compileMatcher` has exactly one implementation, `hooks/lib/match.mjs`; `verify-manifest-coverage.ts` and `ownership.ts` both import it from there, so a matcher change cannot land in one copy and miss the other.

**Ownership of a delivered file is content-keyed, not path-keyed.** `.claude/hooks/` sits outside the sync manifest's content root, so there is no recorded hash to tell PRISM's older copy from a consumer's hand-edit the way `applyIncomingFile` can. The `HOOK_RUNTIME_MARKER` line the shipped files carry is the only signal available. A marked file is PRISM's content at whatever version wrote it. A marked file at a delivered path is replaced without a backup by `deliverHookRuntimeFile`. A marked file anywhere else under `.claude/hooks/` is backed up and removed by `pruneStaleHookRuntimeFiles`. An unmarked file at a delivered path is the consumer's, so it is preserved as `.bak` before PRISM's copy replaces it. An unmarked file at any other path is never touched.

**Ownership of a registration is pattern-keyed, and the two rules answer different questions.** `mergeHookEventEntries` claims an entry only when its command matches the host's pattern end to end: `PRISM_HOOK_COMMAND_PATTERN` for `.claude/settings.json` or `PRISM_CODEX_HOOK_COMMAND_PATTERN` for `.codex/hooks.json`. A consumer who wrapped or edited PRISM's command no longer matches it, so their entry is neither refreshed on delivery nor dropped when its host leaves `hosts` — and after a removal it points at a runtime file that is gone. Loosening the anchor to catch that case would let removal delete a consumer's own wrapper, so the compensating control is reporting rather than claiming: doctor's dead-registration check runs on every host mix, not only when `hosts` includes a delivering host. Scoping it to the delivery branch reintroduces exactly the silent case the anchor accepts.

The two paths carry different risk and the code treats them differently on purpose: delivery replaces a marked file without a backup because it runs on every update, while prune backs the file up first because it fires rarely and a marked file at an unrecognized path is plausibly a consumer's own adaptation that carried the marker along.

**Backups are skipped by name, never by content.** `backupConsumerFile` copies byte for byte, so a `.bak` always inherits its source's marker — content is structurally incapable of separating a backup from the file it copied. `pruneStaleHookRuntimeFiles` therefore excludes backup basenames (`BACKUP_BASENAME_PATTERN`, defined beside `HOOK_RUNTIME_MARKER`) before the marker check. Without that filter prune re-selects the backup it just wrote: measured over four update runs as `.bak` → `.bak.bak` → `.bak.bak.bak` → `.bak.bak.bak.bak`, with run N's recovery copy already gone by run N+1.

**A recovery `.bak` is the consumer's to delete, never PRISM's to reclaim.** The name filter's cost is that a genuinely stale marked `.bak` is left in place rather than swept. That is the intended trade — the backup may be the only surviving copy of consumer-authored bytes, and a sweep that reclaims it defeats the guarantee it exists to provide.
